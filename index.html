Carry the One

A transformer trained on ordinary character tokenization gets exactly zero percent of every addition problem right once the numbers run one digit longer than training. The same task, given a representation built for the job, gets them right well past double the training length. The bottleneck was never the attention mechanism.

Addition is the toy problem everyone reaches for when they want to ask whether transformers can learn an algorithm rather than memorize a lookup table, and the standard answer — trained on strings like 128+94=222, one character at a time — is discouraging. Models learn the training range well and then fail completely the moment a problem runs longer, as if the arithmetic they learned was never really arithmetic, just a pattern that happened to fit a few thousand examples. That result held up in this project too, on the very first model we trained. What follows is the record of what changed it, and what didn't.

The baseline, honestly measured

The first model in this project was about as plain as a transformer gets: a 6-layer, 10.7M-parameter GPT, trained on addition problems written out as plain digit strings — 0123456789+=\n as the entire vocabulary, one token per character, next-token prediction, greedy decoding at eval time. Trained on sums with up to 10 digits per operand, evaluated in-distribution and on sums with 11 or more digits it had never seen.

Not an approximate zero — every digit-count bucket, every carry-count bucket, exactly zero, re-verified against a broader test set spanning up to 21 digits long after the fact. Extending the operand by a single digit was enough to erase the model's ability to add entirely, despite 74.8% of in-distribution problems being solved correctly. This is the well-documented failure mode: it isn't that the model can't approximate addition, it's that whatever it learned doesn't extend past the specific lengths it was shown.

What actually changed

Nothing about attention depth, parameter count, or training duration. The architecture that eventually fixed this uses six times fewer parameters than the baseline above. What changed was how a number gets turned into vectors in the first place, and how the model is allowed to read them back out.

Four things that actually mattered

Getting from that 0% wall to reliable extrapolation took a long sequence of architecture variants — disjoint per-place slot encodings, magnitude-aware codewords, repeating combiner blocks, more than a dozen ablations of each. Most of that log isn't worth reproducing. Four findings are.

1

Parallel decoding needs a representation with no missing positions

The fix starts by abandoning autoregressive generation for the answer entirely: every digit of the sum is predicted in parallel, independent of the others, from a single fixed-width vector built explicitly out of one slot per decimal place. That surfaces a subtler problem immediately — short numbers leave most of those slots empty, and "empty" has to mean something to a classifier. Whatever it means gets learned as a property of absolute position, not of the number, and every position sees wildly different amounts of that training exposure. The fix wasn't a smarter empty-slot classifier. It was removing the concept of empty entirely: every number, short or long, is written out with ordinary leading zeros to the same fixed width — 42 and 000 … 00042 encode identically. A model that never has to decide "is this slot occupied" can't get that decision systematically wrong at the positions it rarely sees.

2

A classifier's embedding table throws away most of its own gradient

Each digit 0–9 needs its own learned codeword, and the obvious choice — an ordinary embedding table, unit-normalized before use — turns out to waste the overwhelming majority of the gradient it receives. Splitting the direction of a codeword from its magnitude and giving each its own dedicated parameter, gated by a decode rule that scores candidates by (a version of) squared distance rather than raw dot product, recovers that gradient and closes a free-lunch loophole a plain classifier has: scaling every class vector up uniformly used to look like more confidence for free. Under the corrected rule it isn't. Magnitude ends up doing real representational work instead of quietly saturating.

3

A fixed-depth recurrent combiner is brittle to depth mismatch, and fixing that costs something real

Carry propagation is a sequential dependency — adding one to a run of nines has to ripple all the way down the number — so the block that combines two encoded operands runs repeatedly, the same shared weights applied a fixed number of rounds, deeper for longer numbers. Trained at exactly one round count, that block doesn't just fail to help when run for more rounds than it saw in training: it actively corrupts already-correct answers. Nothing in training ever taught it that leaving a converged answer alone is an option. Training with a variable round count instead fixes that failure mode cleanly, and buys it back at a real cost in length extrapolation — a genuine trade, not a free improvement, and worth knowing about before shipping either version.

4

Hand-designed "mathematically clean" encodings underperformed arbitrary ones

This is the counterintuitive one, and it came out of a deliberate attempt to do better. If digit d is placed at angle 36°×d on a circle, digit-sum becomes literal angle addition — a clean, textbook-motivated encoding for the operation you actually want. It measurably underperformed a codebook with no imposed structure at all, learned from a random start, at every dimensionality tested. So did a second, even more literal attempt: encoding digit value directly as vector magnitude, so that addition becomes literal vector addition. Both hit the same wall as the encoding got smaller and more "elegant" — accuracy that held up at moderate width and degraded, sometimes catastrophically, as the representation was forced toward the minimal form the mathematics seemed to call for. An arbitrary, freely-learned codebook at a moderate width (3 dimensions per digit, out of 384 available) beat every deliberately-structured alternative tried, including the ones built specifically to make the combiner's job easier on paper.

The headline comparison

The architecture that resulted from those four findings — call it the closed answer, since nothing tried afterward beat it — uses a disjoint per-place slot encoding, the direction/magnitude-split codewords from finding 2, zero-padded representations from finding 1, and a repeating combiner block held at a fixed round count. 1.79M parameters, trained on sums up to 20 digits long.

Compare that against the baseline's cliff: 74.8% in range, exactly 0% one digit past it. Same underlying task, a model with roughly a sixth of the parameters, no additional training tricks beyond the representation itself.

A wilder variant, kept separate on purpose

One more experiment is worth including, clearly labeled as answering a different question than the one above. Positional decimal representation isn't the only way to encode a number, and it's the reason addition needs carry propagation at all: represent a value instead by its residues modulo a set of coprime numbers — a Residue Number System — and addition becomes fully independent per residue channel, no carry, no dependency between channels whatsoever.

Trained on sums up to only 10 digits — the same range the original baseline failed past — this representation generalized to sums more than double that length with no measurable accuracy loss at all, not the graceful decay the positional version shows:

That flat line followed by a hard wall, instead of a decay curve, is the signature of eliminating the dependency structurally rather than learning to manage it: within the representation's capacity there's no sequential chain to get right or wrong, so nothing degrades — and past capacity, reconstruction is mathematically impossible, not merely hard. It's a genuinely different, striking result. It's also not an answer to the question this piece opened with. It works because it designs the carry dependency out of the number system, not because it demonstrates anything about a combiner's ability to learn carry propagation itself. Interesting enough to record, wrong shape to serve as the headline result.

What this doesn't show

Scope, stated plainly

This isn't "the same transformer with a better tokenizer." The comparison architecture predicts every output digit in parallel rather than generating token by token, encodes each operand through a dedicated non-autoregressive module, and runs its combining step for a variable, learned number of rounds rather than a fixed forward pass. Those are real architectural choices doing real work, not merely a different embedding lookup table sitting in front of an otherwise-standard GPT.

What's demonstrated cleanly is narrower and still, I think, worth the length of this post: the standard failure mode is not inevitable, and it does not require more scale, more depth, or more training to fix — a model a sixth the size of the failing baseline, given a representation built for the structure of the problem, solves it. Whether that same fix is available to a purely embedding-level intervention on an otherwise-unmodified autoregressive transformer is a genuinely open, separate question this project didn't test.

Where this leaves things

It was never the attention.

Every failure diagnosed along the way traced back to how numbers were being written into and read out of the model's residual stream, not to any limit on what the attention and feed-forward layers underneath could compute once that representation was fixed. Get the representation right — no missing-slot ambiguity, no wasted gradient in the embedding table, enough repeated depth for the dependency structure the operation actually has, and no premature "cleverness" collapsing the representation smaller than it can afford to be — and a perfectly ordinary transformer block carries the one just fine.
